# Amazon ML Challenge 2026: End-to-End Entity Resolution Approach

This document outlines the complete, highly-optimized architecture we built to achieve top-tier performance on the Business Entity Resolution leaderboard.

---

## 1. The Core Challenge
The task is to link 1.7 million "Source 1" entities to 10 million "Source 2 & 3" entities. Comparing every record against every other record ($O(N^2)$) would require **17 trillion comparisons**, which is computationally impossible. 

Furthermore, the leaderboard evaluates using a **Macro-Average F0.5 Score**, meaning:
* Precision is heavily favored over Recall.
* Correctly predicting that an entity has **zero matches** (a "singleton") gives a perfect score of 1.0 for that entity.
* A single false positive on a singleton tanks that entity's score to 0.0.

---

## 2. Dataset Construction & Hard-Negative Mining
Initially, the model struggled because it was only trained on "Positive" matches (ground truth pairs). It had never seen a "similar but incorrect" pair, causing it to over-predict matches.

**The Solution:**
We wrote `mine_hard_negatives.py`. This script ran a blocking algorithm over the training data to intentionally find candidate pairs that looked very similar (e.g., same city, similar name) but were **not** in the ground truth. 
* We combined the 7.6 Million ground truth positive pairs with 4.6 Million mined "Hard Negatives".
* This resulted in a robust **12.2 Million row training dataset**, forcing the model to learn the subtle differences between true entities and coincidental similarities.

---

## 3. High-Recall Candidate Generation (Blocking)
To feed candidates to the ML model quickly, we use an inverted-index blocking strategy. Our initial strategy capped out at ~65% recall (meaning we instantly lost 35% of true matches before the ML model even saw them!). 

We redesigned the blocking strategy to be incredibly flexible, successfully raising the Candidate Recall ceiling to **~94% - 98%**. For every test entity, we check for candidates using:
1. **Exact Name Match**: Fast mapping of identical names.
2. **Domain Name Extraction**: Candidate names are often URLs (e.g., `MoyaWinvest.com`). We strip spaces and `.com/.net` to catch these matches.
3. **Single Word Overlaps**: We index every word > 2 characters. If a single word matches, we calculate a quick fuzzy ratio (>= 65) to keep it. This catches heavy typos.
4. **Cross-Lingual Address Numbering**: Some candidates have names in Hindi/Bengali, but their addresses retain English numbers. We index the address numbers, and if the numbers match, we verify the address text similarity (>= 65). 

This optimized index generates a tight pool of **~22.6 Million highly probable candidate pairs** for the ML model to evaluate.

---

## 4. Feature Engineering
For every candidate pair generated by the blocking stage, we compute **11 fast mathematical features**:
* **Name Similarities**: Rapidfuzz Ratio, Token Set Ratio, Token Sort Ratio.
* **Core Name Similarity**: We dynamically strip legal suffixes (`LLC, Inc, Pvt, Ltd`) from both names and compare the root words.
* **Address Similarities**: Rapidfuzz string similarities on cleaned addresses.
* **Exact Matches**: Boolean (0/1) flags if the Country, Address Number, or Core Names are perfectly identical.

---

## 5. The Deep Entity Matcher (Neural Network)
We built a custom PyTorch Deep Learning model (`DeepEntityMatcher`) optimized for Apple Silicon (MPS). 
* **Architecture**: A 3-layer Deep Residual Network (ResNet style).
* **Internals**: Uses LayerNorm and GELU activations with Dropout (0.15) to prevent overfitting.
* **Output**: It ingests the 11 feature scores and outputs a continuous probability between `0.0` and `1.0`.

---

## 6. Macro-F0.5 Threshold Calibration
Because the Amazon leaderboard penalizes false positives on singletons so aggressively, a standard threshold of `0.50` yields terrible results. 

We wrote a custom calibration script (`calibrate_macro.py`) that simulated the exact Amazon ML leaderboard metric (Macro-F0.5) against a validation holdout set. 
* We tested 100 different thresholds.
* The math proved that a strict threshold of **`0.61`** is the global optimum. 
* This threshold aggressively rejects weak matches (protecting the singletons) while retaining enough confidence to hit a local F0.5 validation score of **0.9572**.

---

## 7. Pipeline Execution & Submission
The final pipeline (`run_pipeline_v2.py`) ties it all together autonomously:
1. Rapidly builds the 4 inverted indices in memory.
2. Streams through the millions of Source 2 & 3 records, grabbing the 22.6M candidate pairs.
3. Computes the 11 features on the fly.
4. Batches them through the Neural Network on the GPU.
5. Applies the `0.61` strict threshold.
6. Formats the outputs into `matching_results_V3.tsv` and `candidate_pairs_V3.tsv` exactly according to Amazon's strict string formatting rules (comma-separated, alphabetically sorted, empty strings for singletons).
